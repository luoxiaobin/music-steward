# Architecture

## Processes

| Process | Role |
|---|---|
| **App** (`music-steward app` or `serve`) | Python 3.12. Runs the local web server (127.0.0.1 only) and the background jobs (scan, hash, recognition queue, plan, apply, undo) in threads. `app` shows the UI in a native window (pywebview: system WebKit on macOS); `serve` in a browser tab. |
| **Recognition workers** | One short-lived Python process **per album** (`music_steward.recognize.worker`), run one at a time by the queue. beets keeps process-wide state, so a fresh process per album is the isolation (evidence report, finding F1). A worker writes its results to the database and exits. |
| **External programs** | `ffprobe` (audio properties), `ffmpeg` (audio hashes, cue-track slices, previews), `fpcalc` (Chromaprint fingerprints). Started as subprocesses; they only read the collection. |
| **Command line** | The same engine without the UI (`music-steward scan / recognize / plan / apply / resume / undo …`). |

## Components

| Module | Responsibility |
|---|---|
| `scanner.py`, `probe.py`, `tags.py`, `hashing.py`, `audit.py` | Inventory: list files, read properties and tags (with GBK/Big5 repair proposals), tag-independent audio hashes, audit filters. Read-only. |
| `recognize/units.py` | Group files into albums: folders, discs of a set, cue-sheet image albums, singles. |
| `recognize/beets_adapter.py` | The only module that imports beets: matching against MusicBrainz, Deezer, Discogs and AcoustID; in-memory tag repair; fingerprints of cue-track slices. |
| `recognize/queue.py`, `worker.py`, `results.py` | Resumable queue, one process per album; confidence rule (Ready, Likely, Needs review, Weak, No match). |
| `recognize/local.py` | "Own info": a release built from the album's cue sheet, tags, file names or folder name. |
| `recognize/httpcache.py` | Cache of web answers and fingerprints; per-service throttling. |
| `apply/plan.py`, `naming.py` | Frozen plan: destination paths, naming rules, tag values, conflicts, duplicate albums, generated cue sheets. |
| `apply/protocol.py`, `tagwrite.py`, `runner.py` | Journal-first apply: copy → tag the copy → verify → publish (no overwrite); resume; undo. |
| `cue.py`, `chinese.py`, `search.py`, `preview.py`, `settings.py`, `i18n.py` | Cue sheets (encodings, rewrite), Simplified/Traditional, search index with pinyin, audio previews, settings, interface languages. |
| `server.py`, `web/` | HTTP API and the plain HTML/CSS/JS interface (no framework, no external requests). |
| `db.py` | SQLite app database (WAL), schema and migrations. |

## Safety boundaries

* **Read-only sources.** Only `apply/protocol.py` writes music files, and only under the plan's destination root;
  `plan.check_destination` refuses a destination that overlaps a collection root.
* **Journal first.** Every apply step is recorded on the local disk before it happens; temporary files carry the run
  and step in their name; recovery decides from the journal and the files, never from guesses.
* **Publish without overwrite.** Probed per destination: `renamex_np(RENAME_EXCL)` → `link()+unlink()` →
  claim-then-rename (NAS shares; has a documented residual window) → otherwise refuse. See [RECOVERY.md](RECOVERY.md).
* **Local web UI.** Bound to 127.0.0.1; a one-time token becomes an HttpOnly, SameSite=Strict cookie; Host-header
  check; Content-Security-Policy; POST requests need an `X-MLT` header. Keys come from the environment only.
* **Interface translation never touches data.** `web/i18n.js` only translates text that matches the interface
  dictionary; patterns have typed slots so an album title can't be mistaken for interface text.

## Data

One SQLite database (`~/.music-steward/library.sqlite`) holds roots, files (properties, tags, hashes), recognition
units and candidates, decisions and edits, plans and plan items, runs, settings and the search index. Apply journals
are JSON-lines files next to it. See [CONFIGURATION.md](CONFIGURATION.md#where-the-app-keeps-its-data).

## Tests and CI

`python -m pytest`: about 170 tests, with audio generated by FFmpeg at test time (no real music in the repository).
They cover scanning, hashing, tag repair, cue sheets, recognition (with fake matchers), confidence, own info, plans,
apply/resume/undo with injected crashes, settings, search, languages and the HTTP server. GitHub Actions runs them on
Linux and macOS for every pull request; `main` accepts changes only through pull requests that pass.

Measured on the real collection, with methods and numbers: [`m0/EVIDENCE_REPORT.md`](../m0/EVIDENCE_REPORT.md) (M0
experiments) and [`docs/PLAN.md`](PLAN.md) (trial log).
